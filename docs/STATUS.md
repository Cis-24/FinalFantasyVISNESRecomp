## Event engine AOT break: cause (10-29)
**Cause:** codegen bug in snesrecomp `recompiler/v2/codegen.py`, `_emit_indirect_dispatch`. For `JMP (abs)` (opcode `$6C`) the jump pointer is read with `cpu_read16(cpu, cpu->PB, 0x....)`, i.e. from the program bank. According to the 65816 (and to the docstring of the same file, line ~1355) it lives in bank 0; the target bank is PB. Two branches are affected: local goto (~line 1537) and `value_pointer_dispatch` without an index (~line 1635). `JML [abs]`, `JMP/JSR (abs,X)`, the helper `_live_indirect_target_expr` and the interpreter (`interp816.c`, `case 0x6c`) are correct. In the framework tests the games run in bank 00, where PB = 0, which is why the bug went unnoticed.
- **Effect in FF6:** in AOT ExecEvent the event dispatch `jmp ($002a)` (event.asm:183, `C09B59`) reads the ROM word `AB48` from `C0:002A` instead of the WRAM pointer. No case matches; via `dispatch_oob` the code tail-jumps into the interpreter at `C0AB48`, in the middle of the `jsr` of EventCmd_6a. After that garbage runs, the event state is zeroed from frame 50 on, and the title code `7E5000` is never reached.
- **Evidence:** case scripts `work/aot_case.py`, `case_build.sh`, `case_run.sh`, `case_cmp.py`, `fix_verify.sh`; logs `work/logs/case_*`.

  2. Frame 48 (`SNESRECOMP_IBRWATCH`, `SNESRECOMP_TRAP_YIELD`): `jsr ExecEvent` at `C000DA` enters AOT, and in 105 the return into the interpreter lands at `C0AB48`. In 107 ExecEvent jumps back to its own entry even before the dispatch and then runs interpreted; the faulty read never runs natively there. That explains the cascade pattern of the bisection.

## Reference mismatch (r01 title, snes9x reference vs. recomp), resolved 10-29
Result: `compare_dumps.py work/ref/r01 work/run/r01_idle title` is green (exit 0): WRAM 0 unmasked, VRAM 0, framebuffer 0 (5-bit comparison). The stock reference cannot provide CGRAM/OAM.

The stock snes9x reference delivers RGB565, and the 8-bit expansion of the 6-bit green differs from that of the 5-bit SNES value. In the native 5-bit space (each channel `>> 3`) the framebuffers at t28..t34 and at the title dump are pixel-identical. `compare_dumps.py` therefore automatically compares in 5 bits when the reference reports `fb_core_pixel_format = RGB565` (`--fb-8bit` forces 8 bits). Run against run stays 8 bits.
- **WRAM `$15D5-6`, `$15E9-C`:** dead CPU stack (`$1508-$15FF` according to field-ram.txt, S=`$15FF` from reset.asm:17). The live title frame `$15ED-$15FF` (return addresses `C000DD`, `C0B96F`, `$50BD`) is equal; the title main loop waits in WaitVBlank with S=`$15EC`. Below that, the reference holds the NMI frame (P=`$A1`, PC=`7E7208`), the recomp holds JSR leftovers of the sprite routine (`$753B`/`$7558`). The content depends only on the dump phase relative to the NMI. Mask `$1508-$15EC` (tag `title`) with this justification in `validation/masks.toml`. The earlier "nondeterminism" observation at `$15D5` concerned different builds; r01i9, r01_422 and r01_idle are equal there.
- **Game logic in sync per frame:** WRAM without the stack is bit-identical to the reference at t28..t34 (N frames after `$19==9` each).
- **212-frame offset (fixed 10-29, see "Framework patch: DSP power-on values"):** it arises entirely before the splash (splash state 1: ref frame 155, recomp 367; after that the gaps 376/1454/1457 are identical). The SPC upload `InitSound` ends in both at frame 21 (marker `$11FA = $40`). According to the APU ring buffer (dumps b100/b200/b279 in `work/run/b360`) the CPU writes the PlaySong command at frame 58 (port 2 = `00`, port 1 = `02`, port 0 = `$10`; sound_main.asm:304-313, wait loop `C501B5`). But the SPC only reads port 0 at frame 270 and acknowledges immediately. In between there is not a single SPC port event, although the sample counter runs normally (31107 -> 144556 = 3.55 s at 32 kHz). So the SPC runs but does not poll port 0 for 212 frames. Not masked, it only affects the boot duration, not the title image.
- **Cause of the offset (resolved 10-29):** the power-on content of the DSP register EDL (`$7D`) differs.
  - Measurement: `SNESRECOMP_APURAM_TRACE_FILE` (log `work/logs/apuram_280.jsonl`). Between frame 22 and 266 not a single byte in APU RAM changes. The stack bytes show the call chain `$025F` -> `$100B` -> `$1040`.
  - Disassembled (driver block `ff6/build/en/bin/spc.bin`, loaded at `$0200`; helper script local only):
    - `$1002` sets the new EDL (`$80` = 5).
    - `$1015` blocks echo writes (FLG |= `$20`) and reads the **old** EDL (`$7D & $0F`) into `$81`.
    - `$0FEF` waits until timer 1 (target `$80`, 16 ms) has ticked `mem[X]` times (`MOV A,#0 / MOV Y,$FE / BEQ / INC A / CMP A,(X) / BNE`).
  - In `dsp_reset` (snesrecomp `runner/src/snes/dsp.c`) the runtime sets all DSP registers to 0 (only ENDX = `$FF`). An old EDL of 0 means the loop goes all the way round once, 256 ticks × 16 ms = 4.10 s ≈ 246 frames. That matches the silence 21 -> 267 exactly. Then come 5 ticks for the new EDL (until 271), then the acknowledgement.
  - In snes9x the SPC is done before frame 58, so its power-on EDL is not 0. Since confirmed from the source: EDL reads `$4E`, i.e. 14 ticks (see "Framework patch: DSP power-on values").
  - Assessment: the DSP register content after power-on is undefined on real hardware, so the runtime does nothing illegal. It only differs from the reference. This can only be aligned in the framework (power-on values in `dsp_reset`). `game_rtl.c` is not enough, because `initialize()` runs before `snes_reset` (common_cpu_infra.c:1121-1123).

## Framework bug: plp in table target functions (11-03)
**Symptom:** with the battle promotions, r05 hung before the first menu; the interpreter ran into the zero page (95% of the cycles at `$00:0003`) and WRAM `$0001-$2000` was overwritten with `B5 05 00 00`.
- **Narrowing down:** diagnostic build with `SNESRECOMP_EMIT_AOT_DENY_GATE=1` (`work/r05_gate_build.sh`; every AOT function then checks `SNESRECOMP_LLE_INTERP_TARGET_FILE`). Runtime bisection over the 1141 new promotions (`work/r05_bisect.py`, criterion: first battle menu reached, 30-130 s per test, 12 tests): `ValidateSpellList` (`C2568D`, battle/party.asm:725) as AOT breaks on its own. Cross-check: all 1141 denied = good, all AOT = bad. An A/B dump after InitBattle (`work/r05_vsl_pair.sh`) shows the overwrite.
- **Cause:** on entry `ValidateSpellList` saves `phx` and `php` (entry M1X1, so X is 1 byte) and then switches with `longi`. The loop branches via `jmp (AddToSpellListTbl,x)` (`C256F3`). The codegen turns this into tail calls into separate functions `bank_C2_5704/570E/5716_M1X0`. Their code runs to the shared end `plp / plx / rts`, and after the `plp` it generates `plx` hard-wired with 16 bits (`cpu_read16`, S+2), although the `plp` restores X=1. S is then off by 1, and the `rts` jumps into nowhere. After a `plp` without its own `php`, the function assumes its own entry width instead of an unknown one.
- **Scope** (`work/plp_audit.py`, grep over `src/gen`): 31 variants with `plp` without their own `php`; only `bank_C2_5704/570E/5716` (plus the mirror `42`) and the sound entry `TfrSong_ext`/`TfrSongScript_ext` (`C50008`/`C5000C`, mirror `45`) have a fixed 16-bit pull after it. The sound case is already AOT in the committed state and unremarkable in r01-r12; it is still suspicious and belongs in the same check.
- **Workaround in the game repository:** `ValidateSpellList` is set to `emit = false` by hand in `tools/ff6/symbols_overrides.toml`. `promote_misses.py` no longer promotes such blocked targets and removes them from the block (otherwise the generated block overwrote the hand-set block). Cost: 12 AOT variants. The follow-on misses (`ValidateSpellList`, `InitChars`, `InitBattle`, `Battle_ext`, the landings `C25704/570E`) are listed with a justification in `validation/miss_allowlist.toml`.
- **For the pin session:** change the codegen so that the width after a `plp` without a matching `php` in the same function stays dynamic (or generate table targets inside the parent function as local jumps). Test: function with `php`, `rep #$10`, `jmp (tbl,x)`, the target ends with `plp / plx / rts`, entry X=1. Then lift the block, remove the allowlist entries, run `plp_audit.py` again.
- **Fixed 11-05** (patch 0012, table targets stay local), block lifted, see "Pin session 11-05 (OPT and plp)".
